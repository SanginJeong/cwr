00 · Glossary

용어 풀이

이 문서에 자주 나오는 말을 개발을 처음 보는 사람 기준으로 풀었다.

Supabase
데이터베이스(Postgres), 로그인(Auth), 실시간 연결(Realtime), 파일 저장(Storage)을 한 번에 주는 서비스. 이 프로젝트의 백엔드.
RLS (행 수준 보안)
DB가 '이 사람이 이 줄을 읽거나 고쳐도 되는지'를 직접 확인하는 규칙. 화면에서 버튼을 숨기는 것과 달리 우회할 수 없다.
RPC
DB 안에 만들어 둔 함수를 화면에서 이름으로 부르는 것. 예: 출근 버튼 → clock_in().
BFF · Route Handler
브라우저와 DB 사이에 둔 우리 서버 코드(Next.js의 /api 경로). 브라우저에 줄 수 없는 비밀 키가 필요한 일만 여기서 한다.
service role
RLS를 무시하는 관리자용 키. 계정 생성·로그인 차단에 필요하고 서버(BFF)에만 둔다.
proxy.ts
페이지에 들어가기 전에 로그인 여부를 보고 로그인 화면으로 보내는 Next.js 파일 (예전 이름 middleware).
정책 엔진
출퇴근 기록과 정책을 넣으면 날짜별 정상·지각·결근·휴가를 돌려주는 함수 모음.
순수 함수
같은 입력이면 항상 같은 결과를 내고 바깥(DB, 시계)을 건드리지 않는 함수. 테스트하기 쉽다.
멱등
여러 번 실행해도 한 번 실행한 것과 결과가 같은 성질. 예: 같은 날 반복 일정을 두 번 만들어도 하나만 생긴다.
KST
한국 시간(UTC+9). 오늘·지각 판단은 모두 한국 시간 기준.
FSD
폴더를 app·views·widgets·features·entities·shared 6층으로 나누는 프론트엔드 구조 규칙.
ADR
Architecture Decision Record. '왜 이렇게 정했는지'를 대안과 함께 적은 결정 기록 (docs/decisions).
E2E 테스트
실제 브라우저를 띄워 사용자처럼 클릭하며 확인하는 자동 테스트. 이 프로젝트는 Playwright를 쓴다.
Vitest · PGlite
Vitest는 함수 단위 테스트 도구, PGlite는 Docker 없이 쓰는 가벼운 Postgres(DB 규칙 테스트용).
시드 (seed)
테스트를 위해 미리 넣어 두는 가짜 데이터.
storageState
로그인한 브라우저의 쿠키를 파일로 저장한 것. 테스트마다 다시 로그인하지 않으려고 쓴다.
CI · nightly
CI는 PR마다 자동으로 테스트를 돌리는 GitHub Actions. nightly는 평일 아침 정해진 시각에 전체 테스트를 도는 것.
P0 · P1 · P2
테스트 우선순위. P0 깨지면 서비스를 못 쓰는 핵심, P1 역할별 시나리오, P2 모바일·접근성 등(nightly에서만).

01 · Overview

한눈에 보기

한 줄 요약 화면(브라우저)이 Supabase에 바로 묻고, 비밀 키가 필요한 일만 우리 서버(BFF)가 한다. 지각·정상 판정은 브라우저에서 계산한다.

화면은 브라우저에서 Supabase를 직접 부른다(supabase-js, 권한은 RLS·RPC). service role(모든 권한을 가진 서버용 키)이 필요한 일(직원 등록, 퇴사 시 로그인 차단)만 Vercel의 Route Handler(BFF)가 한다. 근태 판정은 DB가 아니라 브라우저의 정책 엔진이 계산한다.

판정은 저장하지 않는다

  • DB에는 사실(출퇴근·휴가 결정)과 규칙(정책)만
  • attendance_range → 순수 함수 정책 엔진 → 정상·지각·결근·휴가
  • 정책을 바꾸면 지난 기록도 다시 판정 (ADR-007)

권한은 DB가 확인한다

  • RLS + RPC가 실제 권한, 메뉴 숨김·proxy는 사용자 경험용
  • 퇴사 = 비활성화: current_profile_id()가 null
  • 휴가 결정은 where status = 'PENDING'로 먼저 처리한 쪽만 (ADR-006)

스택

  • Next.js 16 · React 19 · TypeScript · Tailwind
  • TanStack Query v5 · Zustand(일부 UI 상태)
  • Supabase Auth · Postgres · Realtime · Storage
  • Vercel(icn1) · GitHub Actions

02 · User flow

유저플로우

한 줄 요약 로그인하면 누구나 '내 근태'에서 시작해 사이드바로 이동한다. 출근·휴가 기록 → 승인 → 자동 판정이 서비스의 중심 흐름이다.

세 장으로 나눴다. 전체 화면 흐름 → 근태·휴가(역할을 넘나드는 핵심) → 협업(칸반·할 일·자유게시판).

2-1. 전체 화면 흐름

로그인하면 모든 역할이 "내 근태"에서 시작하고, 사이드바로 각 영역에 간다. 사이드바 메뉴는 역할에 따라 다르게 보이고(휴가 승인은 팀장·인사담당자, 인사 관리는 인사담당자), 실제 접근은 proxy와 DB가 다시 막는다.

2-2. 근태 · 휴가 (역할별)

인사담당자가 계정과 정책을 만들고, 직원이 출퇴근·휴가를 기록하면, 팀장(또는 인사담당자)이 승인하고, 시스템이 기록과 정책으로 판정해 각자의 화면에 돌려준다. 파란 두 곳이 이 서비스의 핵심 규칙이다: 휴가 결정은 먼저 처리한 쪽만, 판정은 엔진이 매번.

직원 (예: 박지민)

  • 로그인 → /attendance 내 근태 (월 달력, 이번 달 요약, 오늘 카드, 휴가 목록)
  • 사이드바 카드로 출근·퇴근, 모바일은 서랍 카드
  • 휴가 신청·취소, 승인 결과 확인
  • 소속 팀의 칸반·할 일, 자유게시판, 마이 히스토리, 계정 설정

팀장 (예: 김하늘)

  • 직원이 하는 모든 것 +
  • 사이드바 "팀장 · 휴가 승인" 배지 → /approvals 승인·반려, 같은 날 겹침, 팀 휴가 달력
  • 팀 페이지의 "오늘 우리 팀 근태"와 멤버별 근태 칩
  • 팀 생성·수정·멤버 관리는 없음

인사담당자 (예: 이서연)

  • "인사 관리": 구성원 관리, 근태 정책, 휴가 승인(회사 전체)
  • 모든 팀을 멤버처럼 보고, 팀 생성·수정·삭제·멤버 배정
  • 직원 추가(임시 비밀번호 1회 표시), 퇴사 처리·복직

2-3. 협업: 칸반 · 할 일 · 자유게시판

팀 협업은 팀 페이지의 칸반에서 시작한다. 목록을 열어 날짜별 할 일을 만들고 완료하면, 칸반의 열(할 일 · 진행중 · 완료)과 진행 상황이 다시 계산된다. 자유게시판은 회사 전체가 같이 쓰는 공간으로, 검색어·정렬이 URL에 남는다. 모든 역할이 같은 흐름을 쓴다 (인사담당자는 모든 팀).

칸반 열은 저장하지 않고 계산한다

  • 목록에 완료한 할 일만 있으면 완료, 오늘까지 안 끝난 할 일이 있으면 진행중, 나머지는 할 일
  • 할 일을 체크하는 순간 카드가 다른 열로 옮겨 간다 (근태 판정과 같은 "저장 대신 계산" 원칙)
  • 반복 일정은 날짜를 열 때 tasks_for_date가 멱등하게 만든다

자유게시판

  • 목록 /board?q=&sort=: 피드형 무한 스크롤, 베스트 게시글
  • 글쓰기: 이미지 1장을 Storage images에 올리고 공개 URL 저장
  • 상세: 본문 전체(줄바꿈 유지), 좋아요, 댓글. 작성자만 수정·삭제

인증 · 계정 · 라우트 보호

쉽게 말하면 회원가입 없이 회사(인사담당자)가 만들어 준 계정으로만 들어온다. 로그인하지 않으면 어떤 화면도 볼 수 없다.

공개 가입이 없는 회사용 서비스. 계정은 인사담당자가 만든다 (2026-10-10 "계정 없이 둘러보기"·데모 로그인 제거).

어떻게 동작하나

  1. 이메일·비밀번호 로그인 → Supabase Auth가 세션을 쿠키에 저장 → 첫 화면 /attendance
  2. src/proxy.ts가 요청마다 세션을 확인해 비로그인은 /login으로, 로그인 상태의 /login은 내 근태로 보낸다
  3. /admin 아래는 proxy가 is_hr_admin RPC로 한 번 더 확인 (화면 보호용, 실제 권한은 DB)
  4. 퇴사 처리된 계정은 Auth에서 ban → 로그인 시 user_banned를 "퇴사 처리된 계정입니다"로 안내
  5. 로그아웃은 signOut() (기본 global: 그 사용자의 모든 세션 종료)

적용한 것

  • Supabase Auth + @supabase/ssr 쿠키 세션, Next 16 proxy.ts (middleware 후속)
  • 새 계정은 profiles.is_active = false로 시작 → 가입 설정을 잊어도 아무것도 못 한다 (ADR-006)
  • current_profile_id()가 비활성 계정에 null → 모든 RLS·RPC가 한 번에 막힘
  • 로그인 폼 검증: 로그인은 빈 값만 막고 형식 규칙은 비밀번호를 정할 때만 (임시 비밀번호 회귀). 최상위 도메인 2글자 이상

출퇴근

쉽게 말하면 출근·퇴근 버튼을 누르면 서버 시계로 시각이 기록된다. 하루에 한 번만 출근할 수 있다.

버튼으로 기록하고, 시각은 서버가 정한다. 접속 상태(활동 중·자리 비움)와는 별개.

어떻게 동작하나

  1. 사이드바 맨 위 카드("오늘 출퇴근")와 내 근태의 "오늘" 카드에서 출근하기 → 퇴근하기
  2. clock_in RPC: (본인, today_kst(), now())를 넣고 이미 있으면 "오늘은 이미 출근했습니다"
  3. clock_out RPC: 오늘 기록 중 퇴근 전인 행만 갱신. 없으면 "오늘 출근 기록이 없습니다"
  4. 카드는 1분마다 근무 시간을 갱신, 1분 미만이면 "방금 출근했어요", 판정 문구는 정책 엔진으로
  5. 모바일: 헤더에는 상태 표시(내 근태: 근무 중 · 2시간 10분)만, 누르면 내 근태. 출퇴근은 서랍 카드에서 (잘못 누르기 방지)

적용한 것

  • 쓰기는 RPC로만, 시각은 DB의 now()와 KST 기준 today_kst() (ADR-007). 클라이언트 시계를 믿지 않는다
  • unique (user_id, date) + on conflict do nothing으로 하루 한 번
  • TanStack Query 캐시 무효화로 카드·달력·요약이 함께 갱신

근태 판정 (정책 엔진)

쉽게 말하면 '지각인지 정상인지'를 DB에 적어 두지 않고, 화면을 열 때마다 규칙(정책)으로 다시 계산한다. 그래서 규칙을 바꾸면 지난 기록의 판정도 함께 바뀐다.

핵심 설계: 판정 결과를 저장하지 않는다. DB에는 사실(출퇴근·휴가 결정)과 규칙(정책)만 두고, 볼 때마다 순수 함수로 계산한다.

어떻게 동작하나

  1. attendance_range(from, to) RPC가 엔진 입력 모양으로 돌려준다: KST 벽시계 시각, 승인된 휴가만 LEAVE, 적용 정책, 입사일, 서버 기준 오늘
  2. evaluateAttendance가 날짜별로 정상 / 지각 / 결근 / 휴가를 정한다. 주말·입사 전·미래는 판정하지 않고, 오늘은 출근했을 때만
  3. 정책 3종: 자율(기록만 있으면 정상) · 코어타임(코어 시작까지 출근) · 고정(출근 시각 + 유예 N분)
  4. summarizeAttendance → "이번 달 요약", 같은 결과로 달력 칩을 그린다
  5. 인사담당자가 정책을 바꾸면 지난 기록도 새 정책으로 다시 판정된다 (다시 계산할 저장값이 없다)

적용한 것

  • HR-platform의 정책 엔진을 그대로 이식 (순수 TypeScript, 현재 날짜도 인자로 받음)
  • Vitest로 경계값 고정: 유예 정확히 N분, 코어 시작 정각, 자정 근처, 주말, 오늘·미래, 입사 전
  • effective_policy: 개인 정책이 없으면 기본 정책. 조회는 한 번에 93일까지
  • 대안(일별 판정 저장, SQL로 엔진 재작성)은 ADR-007에서 기각: 정책 변경·휴가 승인 때마다 덮어써야 하고 어긋날 수 있다

테스트 3층과 E2E 전체 목록

한 줄 요약 작은 함수 → DB 규칙 → 실제 브라우저, 세 겹의 자동 테스트가 있다. 브라우저 테스트는 PR마다 41개, 평일 아침에 53개가 돈다.

아래 층에서 확인한 규칙은 위 층에서 다시 세세하게 보지 않는다 (ADR-008). E2E는 Supabase 로컬 스택(Docker)에 대고 돌고, 원격 DB면 시작하지 않고 멈춘다. 데이터를 바꾸는 스펙은 시작할 때 테스트 데이터를 다시 만들고(시드), 한 번에 하나씩 돈다. 시드가 날마다 달라서 숫자 대신 변하지 않는 성질로 단언한다 (예: 요약 일수 = 달력 칩 수).

AI 리팩토링 워크플로우

한 줄 요약 사람이 방향과 머지를 정하고, AI가 계획·구현·테스트·확인을 한 바퀴씩 돌린다. 결과는 문서와 메모리에 남아 다음 바퀴로 이어진다.

사람(결정·머지)과 AI 에이전트(Claude Code: 분석·구현·테스트·QA)가 같은 고리를 반복했다. 한 바퀴의 결과는 저장소 문서(로드맵·ADR·QA)와 에이전트 메모리에 쌓이고, 다음 바퀴는 거기서 시작한다. 세션이 끊겨도 맥락이 이어지는 이유다.

01 요구 인터뷰

방향을 먼저 묻는다

  • HR 전환은 인터뷰로 목적·주인공·하지 않을 것까지 확정 (roadmap §0)
  • 선택이 필요한 순간에만 AskUserQuestion으로 추천안과 함께 질문 (예: E2E DB를 로컬 스택으로, 팔레트 유지)
  • 사용자 결정은 문서에 날짜와 함께 남긴다

02 로드맵 · ADR

할 일을 체크리스트로, 결정을 ADR로

  • docs/roadmap.md(H0~H6), docs/roadmap-e2e.md(E0~E7): 단계마다 체크박스와 진행 기록
  • ADR-001~008: 대안과 기각 이유까지 (예: 판정 저장 vs 매번 계산)
  • QA 결과는 docs/qa/에 항목·결과·고친 버그로

03 단계별 구현

기능 브랜치, 한 단계 = 한 커밋

  • feat/h1-roles-accounts … feat/e2e-p2-rest처럼 단계마다 브랜치와 PR
  • 커밋 메시지는 한국어로 무엇을·왜 (예: "fix: 처음 방문하면 사이드바를 펼친 상태로 (E2E에서 발견)")
  • FSD import 규칙을 lint로 강제해 구조가 무너지지 않게

04 자동 테스트

아래 층부터

  • 정책 엔진은 Vitest 경계값부터, RLS·RPC는 PGlite DB 테스트
  • 로컬에 Docker가 없어 E2E는 draft PR로 CI를 돌리고 gh run 로그로 실패를 읽어 고친다
  • CI 조건식 버그(빈 문자열이 거짓이라 P2가 빠짐)처럼 테스트가 안 도는 문제도 개수(PR 대 nightly)로 잡는다

05 브라우저 QA

실제 화면에서 확인

  • Claude in Chrome으로 로그인 → 화면별 확인, 스크린샷으로 판단
  • 테스트로 못 보는 것(디자인, 업로드, 느린 응답)을 여기서 잡는다: 게시판 본문 잘림, 없는 글 빈 화면
  • 운영 DB에 쓰는 동작은 사용자에게 먼저 묻는다

06 · Manual steps

직접 할 일

한 줄 요약 설치 2가지와 운영 DB 정리 2가지. 명령어와 SQL을 그대로 복사해 쓰면 된다.

에이전트가 대신하지 않는 일: 설치, 내 계정에 도구 연결, 운영 DB 삭제.

1. Docker(OrbStack) 설치 → 로컬에서 E2E 돌리기

지금은 E2E가 CI에서만 돈다. 로컬에서 돌면 실패를 바로 재현하고 --ui로 화면을 보며 고칠 수 있다. OrbStack은 Docker Desktop보다 가볍고 Supabase CLI와 그대로 호환된다.

  1. OrbStack 설치와 확인
    # 1) 설치 (둘 중 하나)
brew install --cask orbstack          # 또는 https://orbstack.dev 에서 받아 설치
open -a OrbStack                      # 처음 한 번 실행해 권한 허용
docker info | head -5                 # "Server Version"이 보이면 준비 완료
  2. 프로젝트에서 로컬 스택을 띄우고 테스트
    cd ~/Desktop/side-project/Coworkers

# 2) Supabase 로컬 스택 + 마이그레이션 (첫 실행은 이미지 내려받기로 몇 분)
npm run e2e:db                        # = npx supabase start && npx supabase db reset

# 3) 로컬 스택 주소·키로 .env.e2e 만들기 (원격 .env는 그대로)
npm run e2e:env

# 4) 브라우저 (처음 한 번)
npx playwright install chromium

# 5) 실행
npx playwright test --grep-invert @p2   # PR에서 도는 41개
npm run test:e2e                        # 전체 53개 (P2 포함)
npx playwright test --ui                # 화면을 보면서 한 개씩
npx playwright show-report              # 실패 시 trace·영상

# 6) 끝나면
npx supabase stop
    .env.e2e의 Supabase 주소가 로컬(127.0.0.1·localhost)이 아니면 테스트가 시작하지 않고 멈춘다(assertLocalSupabase). 원격(운영) DB에는 닿지 않는다. 앱은 3100 포트로 따로 뜬다.
  3. 잘 안 될 때: npx supabase status로 스택 상태, npx supabase db reset으로 DB 초기화, 포트 충돌이면 npx supabase stop --all 후 다시.

2. Playwright MCP 연결

에이전트가 Playwright로 화면을 직접 탐색해 시나리오와 셀렉터를 확인하고, 결과를 스펙 파일로 남기는 용도 (ADR-008: MCP는 테스트를 쓰는 도구, CI는 MCP 없이 스펙만 실행). 로드맵 2 E0의 남은 체크 항목이다.

  1. 연결
    # 1) Playwright MCP 연결 (이 프로젝트에서만 쓰려면 --scope project → .mcp.json 생성)
claude mcp add playwright -- npx @playwright/mcp@latest

# 2) Claude Code를 다시 열고 연결 확인
#    프롬프트에서 /mcp → playwright: connected
  2. 로컬 스택을 바라보는 개발 서버 실행 (1번을 먼저)
    # 3) 로컬 스택을 바라보는 개발 서버 (Docker 단계 2~3을 먼저)
set -a; source .env.e2e; set +a
npx next dev --webpack -p 3100
  3. Claude Code에 요청: "Playwright MCP로 http://localhost:3100/login 에서 employee@coworkers.test / e2e-Password-1! 로 로그인해 내 근태까지 탐색해줘" (로컬 테스트 DB의 시드 계정). 내 근태 화면이 열리면 docs/roadmap-e2e.md E0의 두 항목을 체크.

3. 운영 DB에 남은 QA 데이터 정리

H4·H5 QA 때 원격 Supabase에 만든 "9시 고정" 정책과 QA 계정(직원1·팀장1)의 휴가가 남아 있다. 데모를 없앤 뒤로는 자동으로 지워지는 데이터가 없다. 배포 사이트(cwr-one.vercel.app)와 같은 DB다.

  1. Supabase 대시보드 → 이 프로젝트 → 왼쪽 SQL Editor → New query.
  2. 먼저 조회만 실행해 대상과 건수를 확인한다.
    -- ① 지울 대상 확인 (먼저 실행해서 결과를 눈으로 본다)
select id, name, type, is_default from public.policies where name like '%9시%';

select p.id, p.nickname, p.email
from public.profiles p
join public.policies pol on pol.id = p.policy_id
where pol.name like '%9시%';                       -- 이 정책이 배정된 사람

select l.id, p.nickname, l.date, l.status, l.reason
from public.leave_requests l
join public.profiles p on p.id = l.user_id
where p.nickname in ('직원1', '팀장1')
order by l.date;
  3. 정리를 실행한다. :policy_id를 ①에서 본 id 숫자로 바꾸고, 한 트랜잭션으로.
    -- ② 정리. 정책 id(:policy_id)는 ①의 첫 결과에서 확인한 값으로 바꾼다
begin;

-- 배정된 사람은 기본 정책으로 되돌린다 (policy_id = null). 배정이 남아 있으면 삭제가 막힌다 (on delete restrict)
update public.profiles set policy_id = null where policy_id = :policy_id;

delete from public.policies where id = :policy_id and not is_default;

-- QA 계정(직원1·팀장1)의 휴가 신청 전부
delete from public.leave_requests
where user_id in (select id from public.profiles where nickname in ('직원1', '팀장1'));

-- 결과가 ①에서 본 건수와 같으면
commit;   -- 다르면 rollback;
    SQL Editor는 RLS를 거치지 않는 관리자 권한으로 실행된다. ①의 결과가 예상과 다르면(다른 사람이 걸려 있거나 이름이 다르면) 멈추고 확인. 지운 행은 되돌릴 수 없다.
  4. 화면으로 확인: 실제 인사담당자 계정으로 /admin/policies에 "9시 고정"이 없는지, /admin/approvals에 직원1·팀장1 신청이 없는지.
  5. 원하면 같은 방법으로 QA 계정 자체도 정리할 수 있다: 구성원 관리에서 직원1·팀장1을 퇴사 처리(기록 보존, 로그인 차단). 삭제보다 이쪽을 권한다 (ADR-006).

4. 운영 DB에 남은 예전 데모 데이터 · 일시정지

데모를 없애면서 매일 리셋하던 크론도 없앴다. 그래서 배포 DB에는 예전 데모 회사(@coworkers.test 30명, 팀 4개, 기록)가 그대로 남고 더는 바뀌지 않는다. 또 그 크론이 매일 DB를 깨워 무료 플랜의 '7일 미사용 일시정지'를 막고 있었는데, 이제는 막아 주는 것이 없다.

  1. 남은 데이터 확인 (SQL Editor, 조회만)
    -- 예전 데모 회사 데이터가 얼마나 남았는지 (조회만)
select count(*) as accounts from public.profiles where email like '%@coworkers.test';

select count(*) as records
from public.attendance_records r
join public.profiles p on p.id = r.user_id
where p.email like '%@coworkers.test';

select id, name from public.groups where name in ('개발팀', '디자인팀', '마케팅팀', '영업팀');
  2. 정리 방법 고르기
    • 그대로 둔다: 예시 데이터로 화면을 보여 줄 때 쓸모가 있다. 데모 로그인이 없어졌으므로 실제 인사담당자 계정으로 본다.
    • 로그인만 막는다 (권장): 실제 인사담당자로 구성원 관리 → 데모 계정마다 퇴사 처리. 기록은 남고 로그인은 막힌다.
    • 지운다: 대시보드 → Authentication → Users에서 @coworkers.test 사용자를 삭제하면 프로필과 기록이 함께 지워진다. 되돌릴 수 없으니 1번 결과를 먼저 확인한다.
  3. 일시정지가 걸리면 Supabase 대시보드에서 프로젝트를 다시 켜면(Restore) 된다. 자주 걸리면 무료 외부 모니터(예: UptimeRobot)가 하루 한 번 사이트를 부르게 두는 방법이 있다.
