# ADR-004: 백엔드를 Supabase로 재구성하고, 반복 일정과 권한 규칙을 정한다

## Status

Proposed (초안. 리뷰 후 Accepted로 변경)

## Date

2026-10-05

## Context

- 지금 백엔드는 교육 과정에서 제공받은 API라서 수정할 수 없습니다. 팀 게시판, 현재 활동 중, 채팅 같은 새 기능은 팀 단위 데이터와 실시간 연결이 필요한데 기존 API로는 만들 수 없습니다. 자세한 배경은 [backend-migration-plan.md](../backend-migration-plan.md)에 있습니다.
- Phase 1에서 기존 API의 실제 동작을 확인했습니다([backend-behavior-spec.md](../backend-behavior-spec.md)). 그 결과 아래 문제가 있었습니다.
  - **반복 일정**: 해당 날짜를 처음 조회할 때 task 행을 만듭니다(지연 생성). 그래서 반복 일정을 수정하면 이미 조회된 날짜에는 반영되지 않습니다(spec §2.5).
  - **권한**: 쓰기 요청에서 권한을 거의 확인하지 않습니다. 멤버가 아닌 사람도 그룹을 수정할 수 있고, 일반 멤버가 팀장을 강퇴하거나 그룹을 삭제할 수 있습니다(spec §4.1).
  - **초대**: 수락 API가 요청 본문의 `userEmail`을 그대로 믿어서, 토큰만 있으면 다른 사람을 그룹에 넣을 수 있습니다(spec §4.3).
- 기존 데이터는 옮기지 않고 새로 시작하기로 했습니다.

## Decision

### 1. 플랫폼

Supabase(Postgres, Auth, Storage, Realtime, 서울 리전)를 쓰고, 여러 단계가 필요한 로직은 Postgres 함수(RPC)로 작성합니다. Next.js Route Handler(BFF)는 서버 비밀값이 필요한 곳에만 씁니다. 근거와 대안 비교는 migration-plan §3에 있습니다.

### 2. 반복 일정: "조회할 때 생성"은 유지하되, 생성을 멱등으로 만들고 수정이 반영되게 한다

- `recurrings` 테이블에 규칙(frequency, weekDays, monthDay, startDate)을 저장합니다.
- `tasks_for_date(task_list_id, date)` RPC가 그 날짜에 해당하는 반복 일정의 task 행을 `insert ... on conflict (recurring_id, date) do nothing`으로 만든 다음 조회합니다.
  - `unique (recurring_id, date)` 제약으로 동시에 조회해도 중복 행이 생기지 않습니다.
  - 기존처럼 모든 task가 **숫자 `id`를 가진 실제 행**이 됩니다. 그래서 프론트의 `?task=12`, 댓글, 완료 처리 코드를 그대로 쓸 수 있습니다.
- task에 `is_customized` 플래그를 둡니다. 사용자가 그 날짜의 이름이나 설명을 직접 수정하면 `true`가 됩니다.
- 반복 일정을 수정하면, **오늘 이후 날짜 중 `is_customized = false`이고 완료되지 않은 task**에도 바뀐 이름과 설명을 반영합니다. 빈도나 요일이 바뀌면 그 범위의 task를 지우고, 다음에 조회할 때 새 규칙으로 다시 만듭니다.
- 펼침 규칙은 기존과 같습니다. 날짜는 KST 기준이고, WEEKLY는 0=일요일, MONTHLY는 해당 날짜가 없는 달을 건너뜁니다.

> spec §2.3에서는 "조회할 때는 계산만 하는 가상 task"를 제안했습니다. 하지만 가상 task에는 숫자 id가 없어서, 프론트의 task id 기반 흐름(URL, 댓글, 완료 처리)을 모두 바꿔야 합니다. 그래서 이 방식으로 바꿨습니다. 아래 Alternatives를 참고하세요.

### 3. 권한: 기존 동작이 아니라 프론트 UI의 의도를 따른다 (RLS로 강제)

| 동작                                                                          | 권한                   |
| ----------------------------------------------------------------------------- | ---------------------- |
| 그룹, 할 일 목록, task, task 댓글 조회                                        | 그룹 멤버              |
| 할 일 목록 생성/수정/삭제, task 생성/수정/완료/삭제, 반복 일정 생성/수정/삭제 | 그룹 멤버              |
| task 댓글 작성                                                                | 그룹 멤버              |
| task 댓글 수정/삭제                                                           | 작성자                 |
| 그룹 수정/삭제, 멤버 강퇴, 초대 토큰 발급                                     | ADMIN                  |
| ADMIN 강퇴                                                                    | 불가                   |
| 게시글 조회                                                                   | 누구나 (비로그인 포함) |
| 게시글, 게시글 댓글 수정/삭제                                                 | 작성자                 |

- task 삭제는 **그룹 멤버 모두** 가능합니다. 지금 UI와 기존 백엔드 동작이 같고, 할 일은 팀이 함께 관리하는 대상이기 때문입니다.

### 4. 탈퇴

- 그룹의 유일한 멤버는 탈퇴할 수 없습니다(기존과 같음). 그룹을 삭제해야 합니다.
- **유일한 ADMIN은 다른 멤버가 남아 있으면 탈퇴할 수 없습니다.** 기존에는 허용돼서 ADMIN이 없는 그룹이 생겼습니다. 지금 프론트에는 팀 나가기 UI가 없어서 당장 영향은 없습니다. 팀 나가기 UI를 만들 때 "관리자 위임" 기능도 함께 만듭니다.

### 5. 초대

- 토큰은 `invitations` 테이블에 저장하는 랜덤 문자열입니다. 만료는 72시간이고, 만료 전까지 여러 명이 쓸 수 있습니다(기존과 같음).
- 수락은 **로그인한 사용자 본인**만 처리합니다. 요청에 이메일을 받지 않습니다.

### 6. history

- `user/history`에서 **삭제된(soft delete) task는 제외**합니다. 기존에는 포함됐지만, 사용자가 지운 할 일이 "완료 기록"에 남아 있는 건 의도와 맞지 않습니다.
- 정렬은 `doneAt` 내림차순으로 보장합니다.

### 7. 응답 형태

프론트 타입(`src/shared/api/types/*`)에 맞춰 mapper가 응답을 조립합니다. 기존 API의 필드 중 프론트가 쓰지 않는 것은 맞추지 않습니다. 날짜 형식은 spec §1을 따릅니다.

## Alternatives Considered

### 반복 일정을 가상 task로 (조회할 때 계산만 하고, 상호작용할 때만 저장)

- Pros: 아무도 보지 않은 날짜에는 행이 없음. 규칙을 수정하면 모든 날짜에 일관되게 반영됨
- Cons: 가상 task에는 숫자 id가 없음. URL의 `?task=`, 댓글, 완료 처리, task 상세 조회를 모두 `recurringId + date` 기반으로 바꿔야 함. 그래서 Phase 3의 "화면 코드는 그대로" 원칙과 충돌함
- Rejected: `is_customized` 플래그로 일관성 문제를 대부분 해결할 수 있음. 행이 늘어나는 정도도 사람이 실제로 열어본 날짜 수만큼이라 작음

### 반복 일정 생성 시점에 미래 task를 미리 생성 (예: 1년치)

- Pros: 조회가 단순한 SELECT가 됨
- Cons: 기간 밖의 날짜를 처리할 수 없음. 끝없이 반복되는 DAILY 일정을 표현할 수 없고, 규칙을 수정하면 대량으로 갱신해야 함
- Rejected

### 기존 권한 동작을 그대로 재현

- Pros: legacy와 supabase 모드에서 비교할 때 차이가 없음
- Cons: 보안 구멍을 그대로 옮기는 것. 프론트 UI의 의도와도 다름
- Rejected

### ADMIN 탈퇴 시 가장 오래된 멤버를 자동으로 ADMIN으로

- Pros: 위임 UI가 없어도 됨
- Cons: 당사자 모르게 권한이 생김
- Rejected (보류): 위임 UI를 만들 때 다시 검토

## Consequences

- `GET` 성격의 task 조회가 RPC 안에서 INSERT를 수행합니다. 그래서 task 조회는 PostgREST 테이블 직접 조회가 아니라 RPC로만 합니다.
- legacy와 supabase 모드를 비교할 때, 권한(§3)과 history(§6)는 **일부러 다르게 동작**합니다. QA 체크리스트에 명시합니다.
- RLS 정책은 `supabase/tests`의 pgTAP 테스트로 검증합니다. 기존 백엔드에 있던 권한 구멍(spec §4.1)을 각각 테스트 케이스로 만듭니다.
- 반복 일정의 "그 날짜 하나만 수정"과 "규칙 수정"이 함께 있을 때의 동작(§2)은 Phase 4에서 화면으로 다시 확인합니다.
