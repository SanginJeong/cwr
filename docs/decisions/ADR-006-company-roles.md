# ADR-006: 회사 하나, 3단계 역할, 인사담당자가 직원 등록

## Status

Proposed (DB·BFF·화면 정리 구현됨. 리뷰 필요)

## Date

2026-10-06

## Context

- Coworkers를 HR 서비스로 바꾼다 ([roadmap](../roadmap.md) §0). 근태 정책을 데이터로 다루는 HR 플랫폼이 주인공이고, 팀·할 일은 그 안의 업무 공간이다.
- 지금 구조는 "누구나 가입하고, 팀을 만들고, 초대 링크로 들어오는" 협업 툴이다. HR 서비스에서는 회사가 사람과 조직을 관리한다.
- 데모용 가상 회사 **하나**만 다룬다. 여러 회사(테넌트)는 범위 밖이다.
- 근태(H2)에서 "팀장이 팀원 휴가를 승인"하려면 팀장이 누구인지 DB가 알아야 한다.

## Decision

### 1. 역할

| 역할       | 저장 위치                                     | 할 수 있는 것                                                              |
| ---------- | --------------------------------------------- | -------------------------------------------------------------------------- |
| 인사담당자 | `profiles.company_role = 'HR_ADMIN'`          | 직원 등록, 퇴사 처리, 팀 생성·수정·삭제, 멤버 배정·팀장 지정, 모든 팀 조회 |
| 팀장       | `memberships.role = 'ADMIN'` (기존 값 그대로) | 자기 팀의 공지 지정, 팀 게시판 정리. H2부터 팀원 휴가 승인                 |
| 직원       | 그 외 (`company_role = 'EMPLOYEE'`)           | 소속 팀의 업무 공간, 본인 근태                                             |

- 팀장은 회사 역할이 아니라 **팀마다** 정해진다. 기존 `memberships.role`을 그대로 써서 마이그레이션 없이 기존 데이터가 맞는다. 화면 문구만 "관리자" → "팀장".
- 헬퍼 `is_hr_admin()`. RLS·RPC·BFF가 모두 이 함수로 확인한다.
- **인사담당자는 모든 팀을 멤버처럼 본다**: `is_member()`가 인사담당자에게 true를 돌려준다. `is_member`를 쓰는 모든 정책(팀 페이지, 할 일, 팀 게시판, 팀 채널)에 한 번에 적용된다. 팀장 권한(`is_admin`)은 주지 않는다.
- 팀 생성·수정·삭제와 멤버 배정(`memberships` insert/update/delete)은 인사담당자만. **팀장도 팀원을 내보낼 수 없다.** 팀을 만든 인사담당자는 멤버가 되지 않는다.

### 2. 계정은 인사담당자가 만든다

- 공개 가입, 팀 초대 링크, 카카오 로그인을 없앤다. 면접관은 H6의 원클릭 데모 로그인으로 들어온다.
- 직원 등록: `POST /api/admin/employees` (Route Handler, BFF)
  1. 사용자 세션으로 `is_hr_admin()` 확인
  2. service role로 `auth.admin.createUser` (임시 비밀번호, 이메일 확인 생략)
  3. 트리거가 만든 프로필을 service role로 활성화하고 회사 역할을 정한다. 실패하면 만든 Auth 계정을 지운다
  4. 임시 비밀번호는 응답으로 한 번만 돌려준다
- service role 키(`SUPABASE_SERVICE_ROLE_KEY`)는 서버 환경변수에만 둔다. `NEXT_PUBLIC_` 접두사가 없어서 브라우저 번들에 들어가지 않는다.
- **새 계정은 비활성으로 시작한다** (`profiles.is_active` 기본값 false). 대시보드에서 "Allow new users to sign up"을 끄는 것이 1차 방어이고, 끄는 것을 잊어도 스스로 가입한 계정은 비활성이라 아무것도 할 수 없다.

### 3. 퇴사는 삭제가 아니라 비활성화

- `PATCH /api/admin/employees/{userId}` `{ isActive }`
  1. 사용자 세션으로 `set_employee_active` RPC (인사담당자만, 본인 제외). 그 사람의 auth id를 돌려준다
  2. service role로 Auth ban(사실상 영구) 또는 해제. 로그인 화면은 "퇴사 처리된 계정" 안내를 보여준다
- DB에서는 `current_profile_id()`가 비활성 계정에 null을 돌려준다. 모든 RLS와 RPC가 이 함수를 거치므로 **이미 발급된 토큰이 남아 있어도, ban이 실패해도** 아무것도 할 수 없다.
- 프로필·멤버십·할 일·댓글·(H2) 근태 기록은 그대로 남는다. 팀 멤버 목록(`get_group`)과 (H2) 근태 판정에서는 뺀다.
- 다시 활성화하면 원래 팀으로 돌아온다(복직).
- 그래서 **회원 탈퇴(`delete_account`)와 팀 나가기(`leave_group`)를 없앤다.** 탈퇴는 기록을 지우고, 팀 이동은 인사담당자가 한다.

### 4. 화면

- 제거: 회원가입, 팀 참여(`/teams/join`), 팀 페이지의 초대 카드, 카카오 버튼, 계정 설정의 회원 탈퇴
- 인사담당자에게만: 팀 만들기(`/teams/new`), 팀 수정·삭제 메뉴, 멤버 "팀에서 제외" 메뉴. 페이지는 서버에서도 막는다(layout에서 `is_hr_admin`)
- 사이드바 팀 목록: 직원·팀장은 소속 팀, 인사담당자는 회사의 모든 팀
- 소속 팀이 없는 직원에게는 "인사담당자에게 문의" 안내

## Alternatives Considered

### 팀장을 회사 역할로 (`company_role`에 `TEAM_LEADER` 추가)

- Pros: 역할이 한 컬럼에 모임
- Cons: 한 사람이 A팀 팀장이고 B팀 팀원일 수 있다. 어느 팀의 팀장인지는 결국 팀마다 저장해야 한다
- Rejected

### 퇴사 시 Auth 계정 삭제

- Pros: 로그인이 확실히 막힘
- Cons: `profiles`가 cascade로 지워져 근태·할 일 기록이 사라진다. HR에서 퇴사자 기록은 보존 대상
- Rejected (ban + 비활성)

### 인사담당자 권한을 `is_member`와 따로 (`can_view_group` 같은 새 헬퍼)

- Pros: 인사담당자가 팀 업무 공간에 쓰기까지 할 수 있는 점을 막을 수 있음
- Cons: `is_member`를 쓰는 정책·RPC가 20곳이 넘어 모두 바꿔야 함. 데모 회사 하나에서 인사담당자의 쓰기를 막을 이유가 약함
- Rejected (필요해지면 그때 나눈다)

### `/teams/new`를 없애고 H5 관리자 화면에서 팀 생성

- 로드맵 초안은 "팀 만들기 화면 제거"였지만, H5 목록에 팀 생성 화면이 없어 인사담당자가 팀을 만들 곳이 사라진다. 기존 화면을 인사담당자 전용으로 남겼다.

## Consequences

- H2 근태 RLS는 "본인 / 팀장(`is_admin`) / 인사담당자(`is_hr_admin`)"로 바로 쓸 수 있다.
- `policy_id`(직원의 근태 정책)는 `policies` 테이블이 생기는 H2에서 추가한다.
- 직원 목록·정보 수정·팀 배정 화면은 H5(구성원 관리)에서 만든다. H1에서는 DB 권한과 BFF만 있다.
- 첫 인사담당자는 SQL로 지정한다 (supabase/README.md).
- 인사담당자는 모든 팀의 할 일·게시판에 쓸 수 있다 (위 대안 참고).
