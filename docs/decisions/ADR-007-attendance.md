# ADR-007: 근태 데이터 모델과 판정 방식

## Status

Proposed (DB·엔진·API 구현됨. 리뷰 필요)

## Date

2026-10-06

## Context

- HR 서비스의 중심 기능은 "근태 정책을 데이터로 다루는 것"이다 ([roadmap](../roadmap.md) §0).
- HR-platform(다님)에 정책 엔진이 있다. 자율·코어타임·고정 세 유형을 받아 하루의 상태(정시·지각·결근·휴가)를 돌려주는 순수 TypeScript 함수이고, 경계값 테스트가 있다.
- 역할과 권한은 [ADR-006](./ADR-006-company-roles.md)을 따른다 (본인 / 팀장 / 인사담당자).

## Decision

### 1. 판정은 저장하지 않는다

- DB에는 **사실**(출근·퇴근 시각, 휴가 신청과 결정)과 **규칙**(정책)만 저장한다.
- 상태는 화면에서 정책 엔진으로 매번 계산한다 (`src/entities/attendance/lib/policy-engine`, HR-platform에서 그대로 옮김).
- 정책을 바꾸면 지난 기록도 새 정책으로 다시 판정된다. 판정 결과를 저장하면 정책을 바꿀 때마다 다시 계산해 덮어써야 하고, 두 값이 어긋날 수 있다.
- 엔진은 현재 날짜를 스스로 알지 않는다. 기준 날짜(`today`)는 서버의 KST 날짜를 RPC 응답으로 받는다. 브라우저 시계를 믿지 않는다.

### 2. 테이블

| 테이블               | 내용                                                                                     |
| -------------------- | ---------------------------------------------------------------------------------------- |
| `policies`           | 유형 + 유형별 칸(코어 시작·끝, 출근 시각·유예). 유형에 맞지 않는 칸은 CHECK로 막는다     |
| `profiles.policy_id` | 직원의 정책. null이면 **기본 정책**(`is_default`, 하나만). 쓰고 있는 정책은 지울 수 없다 |
| `attendance_records` | 직원·날짜(KST)당 한 행. 출근 시각 필수, 퇴근 시각                                        |
| `leave_requests`     | 날짜 하나, 대기 / 승인 / 반려, 결정한 사람·시각                                          |

- 정책을 유형별 nullable 칸으로 둔 이유: jsonb보다 CHECK로 모양을 강제하기 쉽고, 화면 폼도 칸이 정해져 있다.
- 휴가의 중복 방지는 `(user_id, date)` 부분 유니크 인덱스(대기·승인만)다. 반려된 날짜는 다시 신청할 수 있다.

### 3. 쓰기는 RPC로만, 시각은 서버가 정한다

| RPC                                         | 규칙                                                                                 |
| ------------------------------------------- | ------------------------------------------------------------------------------------ |
| `clock_in` / `clock_out`                    | `now()`와 KST 날짜. 하루에 출근 한 번, 퇴근 한 번. 퇴근은 그날 기록에만              |
| `request_leave`                             | 내일부터, 평일, 하루 단위. 사유 200자                                                |
| `cancel_leave`                              | 본인의 대기 중 신청만 (삭제). 승인·반려된 것은 기록으로 남는다                       |
| `decide_leave`                              | 신청자 팀의 팀장 또는 인사담당자, 본인 신청 제외. **먼저 처리한 결정이 적용**        |
| `attendance_range`                          | 한 사람의 기록 + 승인된 휴가(`kind: LEAVE`)를 엔진 입력 모양으로, 적용 정책, `today` |
| `team_attendance_range`                     | 팀 전체 (팀장·인사담당자). 퇴사자 제외                                               |
| `set_default_policy`, `set_employee_policy` | 인사담당자                                                                           |

- "먼저 처리한 결정": `update ... where status = 'PENDING'`. 두 사람이 동시에 결정하면 뒤의 update는 앞의 커밋을 기다렸다가 조건을 다시 확인해 0건이 되고, "이미 처리된 신청입니다"를 받는다.
- 시각은 `timestamptz`로 저장하고, 엔진에 줄 때 KST 벽시계 시각(`YYYY-MM-DDTHH:mm:ss`, 오프셋 없음)으로 바꾼다. 엔진은 오프셋이 붙은 값을 받으면 throw한다.
- 대기·반려된 휴가는 엔진에 넣지 않는다 (기록이 없는 것과 같음). 달력의 "승인 대기" 표시는 `leave_requests`를 따로 읽는다.

### 4. 조회 권한 (RLS)

`can_view_attendance(user)` = 본인 **또는** 인사담당자 **또는** 그 사람이 속한 팀의 팀장(`is_team_leader_of`, 본인 제외).
`attendance_records`, `leave_requests` 모두 이 함수 하나로 조회를 연다. 정책은 직원이면 누구나 읽는다 (내 판정 규칙 보기).

## Alternatives Considered

### 일별 판정 결과를 테이블에 저장 (배치 또는 트리거)

- Pros: 통계 쿼리가 빠름
- Cons: 정책 변경·휴가 승인·지난 기록 수정마다 재계산해야 하고 어긋날 수 있다. 데모 규모(30명 × 3개월)에서는 매번 계산해도 충분히 빠르다
- Rejected. 대량 통계가 필요해지면 그때 캐시로 둔다

### 엔진을 SQL(plpgsql)로 다시 작성

- Pros: 서버에서 판정해 내려줄 수 있음
- Cons: 같은 규칙이 두 언어에 생긴다. 엔진의 테스트(경계값)를 그대로 쓸 수 없다
- Rejected. 엔진은 TypeScript 하나로 두고, DB는 엔진 입력을 만들어 준다

### 야간 근무(자정을 넘는 퇴근)

- 퇴근을 전날 기록에 붙이면 "퇴근을 잊은 어제 기록"과 구분하기 어렵다. 범위 밖으로 두고, 퇴근은 그날 기록에만 한다

## Consequences

- H3(직원 화면)은 `getAttendanceRange` → `evaluateAttendance` → `summarizeAttendance`로 달력과 요약을 그린다.
- H4(팀장)는 `team_attendance_range`와 `leave_requests`(RLS로 팀원 것만 보임)를 쓴다.
- H5(인사담당자)의 정책 화면은 `policies`를 직접 insert/update/delete하고, 기본 정책·직원 배정은 RPC를 쓴다.
- 동시 결정은 PGlite(연결 하나)로는 순서대로만 확인했다. 실제 동시성은 Postgres의 행 잠금에 기대고 있다.
- 공휴일, 반차, 연차 잔여일은 범위 밖이다 (roadmap §0).
