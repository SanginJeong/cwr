# 기존 백엔드 동작 명세 (Phase 1 결과)

> 확인일: 2026-10-05
> 방법: 테스트 계정과 임시 가입 계정으로 기존 API(`/18-4`)를 직접 호출. 테스트용 그룹(`probe-spec`)을 만들어 확인한 뒤 삭제했습니다.
> 관련 문서: [backend-migration-plan.md](./backend-migration-plan.md)

각 항목은 **[확인]**(직접 호출해서 본 결과)과 **[추정]**(결과로 미루어 본 것)으로 구분합니다. 새 백엔드에서 어떻게 할지는 **→ 새 백엔드** 줄에 적었습니다.

## 1. 날짜와 타임존

- [확인] 모든 날짜 계산은 **KST(UTC+9) 기준 하루 단위**입니다.
  - `date` 쿼리는 `2026-10-06`이든 `2026-10-06T00:00:00Z`든 `2026-10-05T16:00:00Z`든 KST로 바꿨을 때의 날짜(10-06)로 처리됩니다.
  - task의 `date`는 KST 자정을 UTC로 표현한 값입니다. 예: `2026-10-05T15:00:00.000Z` = KST 10-06 00:00
- [확인] `createdAt`, `updatedAt`, `doneAt`은 `+09:00` 오프셋이 붙은 문자열로 내려옵니다. `date`, `startDate`는 `Z`(UTC)로 내려옵니다.
- [확인] `date` 쿼리를 생략하면 오늘(KST)로 처리됩니다.

**→ 새 백엔드**: task의 날짜는 Postgres `date` 타입(KST 기준 날짜)으로 저장합니다. 응답에서는 기존 형식(KST 자정의 UTC ISO 문자열)으로 바꿔서 내려줍니다.

## 2. 반복 일정(Recurring)과 할 일(Task)

### 2.1 생성

- [확인] `POST .../recurring`의 응답은 **task가 아니라 recurring 객체**입니다. 형태: `{ id, name, description, startDate, frequencyType, weekDays, monthDay, taskListId, groupId, writerId, createdAt, updatedAt }`
- [확인] `startDate`를 생략하면 오늘 KST 자정이 됩니다.
- [확인] `startDate`가 오늘보다 과거면 400 `"시작 날짜는 현재 날짜 이후여야 합니다."`
- [확인] `startDate`는 보낸 값 그대로 저장됩니다. 계산할 때는 KST 날짜로 처리합니다. 예: `2026-10-10T00:00Z`는 10-10에 나타남

### 2.2 날짜별 펼침 규칙

| frequencyType | 규칙                                        | 확인 결과                                                                              |
| ------------- | ------------------------------------------- | -------------------------------------------------------------------------------------- |
| ONCE          | `startDate` 날짜에 한 번                    | [확인]                                                                                 |
| DAILY         | `startDate`부터 매일                        | [확인]                                                                                 |
| WEEKLY        | `startDate` 이후 `weekDays`에 해당하는 요일 | [확인] **0 = 일요일**, 3 = 수요일                                                      |
| MONTHLY       | `startDate` 이후 매월 `monthDay`일          | [확인] **`monthDay=31`이면 30일까지 있는 달(11월)과 2월은 건너뜀**. 말일로 당기지 않음 |

- [확인] `startDate` 이전 날짜에는 나타나지 않습니다.

### 2.3 언제 실제 데이터가 되나 (지연 생성)

- [확인] **해당 날짜를 조회하는 순간 실제 task 행이 생성**되고 새 `id`가 붙습니다. 같은 날짜를 다시 조회하면 같은 `id`가 나옵니다.
  - 조회하는 API(`GET .../tasks?date`, `GET task-lists/{id}?date`, `GET groups/{id}/tasks?date`)는 모두 같은 방식입니다.
- [추정] 아무도 조회하지 않은 날짜에는 task 행이 없습니다. 그래서 반복 일정을 수정하면 "이미 조회된 날짜"와 "아직 조회되지 않은 날짜"의 결과가 달라집니다(§2.5).

**→ 새 백엔드**: 이 지연 생성 방식이 §2.5처럼 일관성 없는 결과를 만듭니다. 그래서 **가상 task 방식으로 바꾸는 것**을 제안합니다.

- 조회할 때는 규칙으로 계산만 하고 행을 만들지 않습니다.
- 완료, 수정, 삭제, 댓글처럼 상태가 생길 때만 `tasks`에 행(예외)을 만듭니다.
- 가상 task의 id는 `recurringId + date`로 식별합니다.
- 단, 프론트가 `taskId: number`를 전제로 하므로, 첫 상호작용 때 행을 만들고 그 id를 쓰는 방식으로 호환시킵니다. ADR-004에서 결정합니다.

### 2.4 완료 처리

- [확인] `PATCH .../tasks/{id}` `{done: true}` → `doneAt = 현재 시각`, `userId`(=doneBy) = 요청한 사용자
- [확인] `{done: false}` → `doneAt = null`, `userId = null`. history에서도 빠집니다.
- [확인] 응답 형태는 조회 응답과 다릅니다. `writer`, `doneBy`, `commentCount`가 없고 `userId`, `writerId`가 있습니다.

### 2.5 수정 범위

- [확인] task 하나를 수정(`name`, `description`)하면 **그 날짜에만** 반영됩니다.
- [확인] 반복 일정을 수정(`PATCH .../recurring/{id}`)하면 **아직 조회되지 않은 날짜에만** 반영됩니다. 이미 조회된 날짜의 task는 이전 이름 그대로입니다.
  - 예: 10-06, 10-14는 이미 조회됨 → "daily" 그대로, 10-20은 처음 조회 → "daily-v2"

**→ 새 백엔드**: 가상 task 방식이면 "수정하지 않은 날짜에는 모두 반영"으로 자연스럽게 일관됩니다. 지금 UI에는 반복 일정 수정 기능이 없어서 영향이 적습니다.

### 2.6 삭제

| 동작                                                   | 결과                                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| task 하나 삭제 `DELETE .../tasks/{id}`                 | [확인] **soft delete**(`deletedAt` 설정). 그 날짜에서만 사라지고 다시 생성되지 않음. 다른 날짜는 그대로. 단건 조회는 404 |
| 반복 일정 삭제 `DELETE .../tasks/{id}/recurring/{rid}` | [확인] **연결된 task 전부 hard delete**. 과거 날짜와 완료된 것 포함. history에서도 사라짐                                |
| 그룹 삭제                                              | [확인] 하위 task까지 hard delete. history에서도 사라짐                                                                   |

- [확인] soft delete된 task는 **history에 계속 남습니다**(`deletedAt`이 채워진 상태로).

**→ 새 백엔드**: 단건 삭제는 예외 행(`deleted_at`)으로 처리합니다. 반복 일정과 그룹 삭제는 FK `on delete cascade`로 처리합니다. history에 soft delete된 task를 보여줄지는 프론트에서 결정합니다(지금은 보여주는 셈).

### 2.7 기타

- [확인] task의 `displayIndex`는 모두 0입니다. 순서 변경 API를 쓰지 않으면 의미가 없습니다.
- [확인] 할 일 목록(task list)의 `displayIndex`는 생성 순서대로 0, 1, 2…입니다. 단, 기존 데이터에는 모두 2인 경우도 있어서 신뢰하기 어렵습니다.
- [확인] `GET user/history`의 정렬 순서는 보장되지 않습니다(doneAt, id 순서 모두 아님). **프론트에서 정렬해야 합니다.**
- [확인] `GET groups/{id}`의 `taskLists[].tasks`에는 **오늘(KST)** task가 포함됩니다. 조회 형태의 task에는 `user`(완료자, `doneBy.user`와 같은 값) 필드도 있습니다.

## 3. 댓글

- [확인] task 댓글: 작성하면 `commentCount`가 늘어납니다. 목록은 페이지네이션 없이 배열로 내려옵니다.
  - 응답 형태: `{ id, content, createdAt, updatedAt, taskId, userId, user: {id, nickname, image} }`
- [확인] 작성자가 아니면 수정/삭제가 403입니다. 메시지: `"댓글 작성자만 수정할 수 있습니다."` / `"댓글 작성자만 삭제할 수 있습니다."`

## 4. 그룹, 멤버, 권한 ⚠️

### 4.1 권한 확인 현황 (중요)

기존 백엔드는 **조회만 멤버인지 확인하고, 쓰기는 대부분 확인하지 않습니다.**

| 동작                            | 멤버가 아닌 사용자     | MEMBER                         | 프론트 UI의 의도                             |
| ------------------------------- | ---------------------- | ------------------------------ | -------------------------------------------- |
| 그룹, task, 댓글 조회           | [확인] 404 `Not Found` | 가능                           |                                              |
| 그룹 수정                       | [확인] **가능**        | [확인] 가능                    | ADMIN만 (`ProgressWidget`)                   |
| 그룹 삭제                       | -                      | [확인] **가능**                | ADMIN만                                      |
| 할 일 목록 생성/삭제            | [확인] **가능**        | [확인] 가능                    |                                              |
| task 완료 처리                  | [확인] **가능**        | [확인] 가능                    |                                              |
| task 삭제 (다른 사람이 만든 것) | -                      | [확인] 가능                    |                                              |
| task에 댓글 작성                | [확인] **가능**        | [확인] 가능                    |                                              |
| 초대 토큰 발급                  | [확인] **가능**        | 가능                           |                                              |
| 멤버 강퇴                       | -                      | [확인] **ADMIN까지 강퇴 가능** | ADMIN만, ADMIN은 강퇴 불가 (`WidgetProfile`) |

**→ 새 백엔드**: 이 부분은 **따라 하지 않습니다.** RLS로 아래 규칙을 강제합니다.

- 조회와 쓰기 모두 **그룹 멤버만** 가능
- 그룹 수정/삭제, 멤버 강퇴, 초대 토큰 발급은 **ADMIN만** 가능
- ADMIN은 강퇴할 수 없음
- 할 일 목록과 task의 생성/수정/완료/삭제는 멤버 모두 가능 (지금 UI 동작 그대로)

### 4.2 탈퇴와 그룹 유지

- [확인] ADMIN이 스스로 탈퇴할 수 있습니다. 그러면 **ADMIN이 없는 그룹**이 남습니다(남은 멤버는 계속 MEMBER).
- [확인] 멤버가 한 명뿐이면 그 멤버는 탈퇴할 수 없습니다. 400 `"그룹에 유일한 멤버는 삭제할 수 없습니다. 그룹을 삭제해주세요."`

**→ 새 백엔드**: 유일한 멤버 탈퇴 금지는 유지합니다. ADMIN 탈퇴는 "다른 ADMIN이 있거나, 다른 멤버에게 ADMIN을 넘긴 경우에만" 허용할지 결정이 필요합니다(§7).

### 4.3 초대

- [확인] 초대 토큰은 JWT입니다. `{ groupId, scope: "invitation", iat, exp, iss: "sp-coworkers-mailer" }`, **유효 기간 72시간**
- [확인] 같은 그룹에 대해 여러 번 발급하면 같은 토큰이 나옵니다(같은 초 안에서는). **일회용이 아닙니다.** 만료 전까지 여러 명이 쓸 수 있습니다.
- [확인] 이미 멤버인 사람이 수락하면 400 `"이미 그룹에 소속된 유저입니다."`
- [확인] ⚠️ **수락 API가 요청 본문의 `userEmail`을 그대로 믿습니다.** 토큰만 있으면 **다른 사람의 이메일로 그 사람을 그룹에 추가**할 수 있습니다. 실제로 이 테스트 중에 본인 계정(sanginjeong07@gmail.com)이 테스트 그룹에 추가됐고, 바로 제거했습니다.
- [확인] 초대를 통해 들어온 사람은 MEMBER가 됩니다.

**→ 새 백엔드**: 수락은 **로그인한 사용자 본인**만 처리합니다. `userEmail`은 받지 않습니다. 토큰은 `invitations` 테이블에 저장하는 랜덤 문자열로 바꾸고, 만료 시간(72시간)을 둡니다. 여러 명이 쓸 수 있는 방식은 유지합니다.

### 4.4 기타

- [확인] 그룹 이름 중복이 허용됩니다(서버 기준). 프론트에서는 `validateTeamName`으로 내 그룹 안에서만 중복을 막고 있습니다.
- [확인] 그룹 생성 응답에는 `teamId`가 없습니다. 생성자는 ADMIN 멤버가 됩니다.

## 5. 사용자

- [확인] **닉네임은 중복될 수 없습니다.** 가입할 때 400 `"이미 사용중인 닉네임입니다."` (`details.nickname.message`)
- [확인] 회원 탈퇴 시:
  - 작성한 게시글이 삭제됩니다. **그 게시글에 달린 다른 사람의 댓글도 함께 삭제**됩니다.
  - 그룹 멤버십이 삭제됩니다.
  - 같은 이메일로 로그인하면 400 `"존재하지 않는 이메일입니다."`
  - [추정] task 댓글도 삭제되고, 완료자(`doneBy.user`)는 null이 되는 것으로 보입니다. 응답 타입에서 nullable로 정의되어 있습니다.
- [확인] 로그인 응답: `{ user: {id, nickname, image, teamId, email, createdAt, updatedAt}, accessToken, refreshToken }`
- [확인] `GET /user` 응답에는 `memberships[]`가 들어 있고, 각 항목에 `group`이 중첩됩니다.

**→ 새 백엔드**: `profiles.nickname`에 unique 제약을 둡니다. 탈퇴 시 게시글은 cascade로 삭제합니다(기존과 같음). task의 `done_by`, `writer_id`는 `on delete set null`로 처리합니다.

## 6. 게시글(Article)

- [확인] `keyword` 검색은 **제목과 내용 모두** 검색합니다.
- [확인] 목록 응답: `{ list, totalCount }`. `orderBy=like`는 좋아요 많은 순입니다.
- [확인] 상세 응답의 `isLiked`: 비로그인이면 `null`, 로그인이면 `true`/`false`
- [확인] 좋아요를 두 번 누르면 400 `"이미 좋아요한 게시글입니다."`, 좋아요 안 한 상태에서 취소하면 400 `"좋아요를 하지 않은 게시글입니다."`
- [확인] 작성자가 아니면 수정이 403 `"게시글 작성자만 수정할 수 있습니다."`
- [확인] 댓글 목록은 **최신순**이고 커서 방식입니다. 응답은 `{ list, nextCursor }`이고, `nextCursor`는 현재 페이지 마지막 댓글의 `id`입니다. 마지막 페이지면 `null`.
  - 댓글 형태: `{ id, content, createdAt, updatedAt, writer: {id, nickname, image} }` (task 댓글은 `user`, 게시글 댓글은 `writer`로 필드명이 다름)

## 7. 결정이 필요한 것 (ADR-004로)

1. **반복 일정 모델**: 가상 task + 예외 행 방식(제안) vs 기존의 지연 생성 방식 그대로
2. **ADMIN 탈퇴**: 허용하지 않음 / 다른 멤버에게 ADMIN 넘기기 / 그대로 허용
3. **history에 soft delete된 task 표시 여부**
4. **task 삭제 권한**: 멤버 모두(지금과 같음) vs 작성자와 ADMIN만
