# 로드맵 2: E2E 테스트 (Playwright)

> 작성일: 2026-10-07 · 이전 로드맵: [roadmap.md](./roadmap.md) (H0~H6 완료, https://cwr-one.vercel.app 배포)

## 0. 목표와 원칙

| 항목                  | 내용                                                                                                                                                                               |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 목표                  | 면접관이 들어오는 데모(로그인 3종과 핵심 흐름)가 **코드를 바꿔도 깨지지 않게** 화면 흐름을 테스트로 고정한다                                                                       |
| 테스트 층             | 순수 함수(Vitest) → DB·RLS(PGlite) → **화면 흐름(Playwright, 이번 로드맵)**. 아래 층에서 확인한 규칙은 E2E에서 다시 세세하게 보지 않는다                                           |
| Playwright MCP의 역할 | **테스트를 쓰고 고치는 도구.** 에이전트가 MCP로 화면을 탐색해 시나리오와 셀렉터를 확인하고, 결과는 `@playwright/test` 스펙 파일로 남긴다. CI는 MCP 없이 스펙 파일만 실행한다       |
| 셀렉터                | 역할·접근 가능한 이름 우선 (`getByRole`, `getByLabel`). 이름이 없는 요소는 테스트 전에 **접근성을 고쳐서** 이름을 붙인다. `data-testid`는 달력 칸처럼 의미 있는 이름이 없는 곳에만 |
| 기다리기              | 고정 대기(`waitForTimeout`) 금지. web-first 단언(`toBeVisible`, `toHaveText`)과 응답 대기(`waitForResponse`)만 쓴다                                                                |

## 1. 먼저 정해야 할 것 (E0에서 결정, ADR-008)

### 1-1. 어느 DB에 대고 돌릴지

지금은 로컬 개발과 배포가 **같은 Supabase 프로젝트**를 쓴다. E2E는 출근·휴가 신청처럼 데이터를 바꾸므로 그대로 돌리면 데모 데이터가 오염되고, 반대로 면접관의 조작이 테스트를 깨뜨린다.

| 안                                                          | 장점                                      | 단점                                                          |
| ----------------------------------------------------------- | ----------------------------------------- | ------------------------------------------------------------- |
| **A. Supabase 로컬 스택 (Docker, `supabase start`)** (추천) | 완전히 격리, CI에서 매번 새 DB, 비용 없음 | 로컬에서 돌리려면 Docker 필요. CI 시작 1~2분                  |
| B. E2E 전용 Supabase 프로젝트                               | Docker 없음                               | 동시에 도는 CI끼리 데이터가 섞임, 무료 플랜 일시정지, 키 관리 |
| C. 지금 프로젝트에 데모와 다른 계정으로                     | 준비 없음                                 | 데모·운영 데이터와 섞임. 추천하지 않음                        |

- H2에서는 DB 테스트를 PGlite로 두고 Docker를 들이지 않기로 했다. E2E는 Auth·PostgREST·Realtime이 모두 필요해서 PGlite로는 안 되므로, **CI에서는 Docker(A)를 쓰는 것으로 결정을 바꾼다.**
- 마이그레이션은 `supabase db reset`으로 적용하고, 데이터는 기존 `GET /api/cron/reset-demo`로 만든다 (같은 시드를 그대로 재사용).

### 1-2. 시간 문제

- **서버 시각은 조작할 수 없다.** 출퇴근·휴가 규칙은 DB의 `now()`·`today_kst()` 기준이다. 브라우저 시계(`page.clock`)만 바꾸면 화면과 서버가 어긋난다. 브라우저 시계는 조작하지 않는다.
- **출근은 하루 한 번**이다. 데이터를 바꾸는 스펙은 시작할 때 `reset-demo`로 되돌린다 (데모 로그인 계정은 오늘 출근 기록이 비어 있게 시드됨).
- **주말에 돌면 결과가 다르다** (주말은 판정하지 않음, 오늘 팀 근태는 "판정하지 않는 날"). 단언은 "오늘이 평일이면 ~, 주말이면 ~"로 나누거나, 평일에만 의미 있는 스펙은 `test.skip(isWeekendKst())`로 둔다.
- **시드 데이터는 날짜마다 달라진다** (오늘 기준 최근 3개월). 정확한 숫자 대신 **변하지 않는 성질**로 단언한다. 예: 요약의 합계 = 달력의 칩 수, 정책을 "05:00 고정·유예 0분"으로 바꾸면 그 직원의 정상은 0일.
- KST 자정 근처(UTC 15:00 전후)에는 실행하지 않는다 (CI 스케줄을 피한다).

### 1-3. 병렬 실행

데모 계정 3개를 모든 스펙이 같이 쓰므로, 데이터를 바꾸는 스펙은 **직렬**(`workers: 1` 또는 `test.describe.configure({ mode: "serial" })`)로 돌린다. 읽기만 하는 스펙은 병렬로 돌려도 된다. 나중에 느려지면 역할별 계정을 워커 수만큼 늘린다 (시드에 `e2e-employee-1..n`).

### 2-5. 역할을 넘나드는 흐름

| #   | 시나리오                                                                  | 확인할 것                                                                   | 우선 |
| --- | ------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---- |
| X1  | 직원 신청 → 팀장 승인 → 직원 달력                                         | 직원 컨텍스트에서 그 날짜가 "휴가" 칩                                       | P0   |

- [x] 출퇴근 카드·요약 카드에 영역 이름 (일부 있음, 빠진 곳 보완)
- [x] 토스트를 `getByRole("status")`로 잡을 수 있는지 확인 (react-hot-toast)
